# Épreuve E5 — Arguments par bloc de compétences pour chaque projet

> Guide de préparation à l'oral de présentation du parcours professionnel.
> Pour chaque projet et chaque bloc coché, voici ce que tu dois dire au jury.

---

## Qu'est-ce que le jury attend par bloc ? (Option SLAM)

Le jury évalue ta capacité à **justifier concrètement** chaque case cochée dans ton tableau de synthèse. Voici ce que tu dois prouver pour chaque bloc :

---

### Bloc 1 — Gérer le patrimoine informatique

**Ce qu'on te demande de montrer :**

| Sous-compétence | Ce que le jury attend en SLAM |
|---|---|
| Recenser et identifier les ressources numériques | Lister les composants de ton projet (serveur, BDD, API, services tiers) et expliquer leur rôle |
| Exploiter des référentiels, normes et standards | Montrer que tu suis des conventions (REST, OpenAPI, MVC, conventions de nommage, PEP8, TypeScript…) |
| Mettre en place et vérifier les niveaux d'habilitation | Expliquer ton système d'authentification et d'autorisation (JWT, rôles, middlewares, routes protégées) |
| Vérifier les conditions de la continuité d'un service | Montrer comment ton service reste disponible (Docker restart, healthchecks, reverse proxy, monitoring) |
| Gérer des sauvegardes | Expliquer comment les données sont protégées (volumes Docker, dumps SQL, versioning Git) |
| Vérifier le respect des règles d'utilisation | Montrer tes protections (rate limiting, validation des entrées, CORS, hash des mots de passe) |

**En résumé** : "Je sais inventorier, sécuriser et maintenir les ressources de mon projet."

---

### Bloc 2 — Répondre aux incidents et aux demandes d'assistance et d'évolution

**Ce qu'on te demande de montrer :**

| Sous-compétence | Ce que le jury attend en SLAM |
|---|---|
| Collecter, suivre et orienter des demandes | Montrer que tu as reçu des demandes (du tuteur de stage, du formateur, d'utilisateurs) et que tu les as organisées |
| Traiter des demandes concernant les services réseau et système | Peu pertinent en SLAM — plutôt SISR |
| Traiter des demandes concernant les applications | Montrer des exemples concrets de bugs corrigés, fonctionnalités ajoutées, évolutions demandées |

**En résumé** : "On m'a demandé des choses, je les ai traitées." C'est beaucoup plus facile à justifier en **stage** (demandes réelles du tuteur/client) qu'en projet de formation.

# PROJET 3 : Evencia — Backend (API REST Express.js)

**Description** : Création du backend d'une application web dédiée à la gestion sécurisée des utilisateurs, des événements et des réservations via une API REST.
**Période** : Septembre 2025 – Mars 2026
**Technologies** : Node.js 20, Express.js 4, JWT, bcrypt, express-validator, express-rate-limit, Swagger/OpenAPI 3, Stripe, MySQL 8, Drizzle ORM, Docker

---

## Bloc 1 — Gérer le patrimoine informatique

**Sous-compétences mobilisées :**
- Recenser et identifier les ressources numériques
- Exploiter des référentiels, normes et standards
- Mettre en place et vérifier les niveaux d'habilitation
- Vérifier les conditions de la continuité d'un service informatique
- Gérer des sauvegardes
- Vérifier le respect des règles d'utilisation des ressources numériques

**Argument au jury :**

> « **Recensement des ressources** : j'ai identifié et documenté l'ensemble des ressources nécessaires : base MySQL 8.0 pour le stockage, serveur Node.js/Express pour l'API, service Stripe pour les paiements, Docker pour la conteneurisation. Tout est documenté dans le README et la documentation technique.
>
> **Normes et standards** : j'ai respecté l'architecture REST (verbes HTTP GET/POST/PUT/DELETE, codes retour 200/201/400/401/403/404), le standard JWT (RFC 7519) pour l'authentification, et OpenAPI/Swagger pour documenter l'API automatiquement sur /api-docs.
>
> **Habilitations** : le système gère 3 rôles (admin, organizer, participant) avec deux middlewares : authenticateToken vérifie le JWT, et authorizeRoles contrôle que l'utilisateur a le bon rôle. Par exemple, créer un événement nécessite le rôle "organizer" ou "admin", un participant ne peut que consulter et s'inscrire.
>
> **Continuité** : Docker Compose avec la politique restart: unless-stopped assure le redémarrage automatique. Le healthcheck MySQL (mysqladmin ping) garantit que le backend ne démarre qu'une fois la base saine (depends_on: condition: service_healthy).
>
> **Sauvegardes** : les données MySQL sont persistées dans un volume Docker nommé (mysql_data). Les migrations SQL versionnées permettent de recréer la structure à tout moment. Le code source est sur GitHub.
>
> **Règles d'utilisation** : express-rate-limit prévient les abus (100 req/min global, 5 req/min sur login). express-validator vérifie les entrées. Les mots de passe sont hashés avec bcrypt. Le CORS n'accepte que les origines autorisées. »

---

## Bloc 2 — Répondre aux incidents et aux demandes d'assistance et d'évolution

**Sous-compétence mobilisée :**
- Traiter des demandes concernant les applications

**Argument au jury :**

> « Pendant le développement, j'ai traité des demandes d'évolution : l'ajout de la gestion des catégories d'événements (migration SQL 003_add_category_and_tickets.sql avec les champs category, max_tickets, image_url), le passage des identifiants auto-incrémentés aux UUID pour des raisons de sécurité (migration 002), et l'intégration du paiement Stripe qui n'était pas prévue dans la version initiale.
>
> J'ai aussi corrigé des incidents identifiés lors des tests Postman : erreurs de validation, problèmes de CORS, gestion des cas limites (double inscription, token expiré). Le middleware errorHandler centralise la gestion des erreurs pour fournir des messages cohérents. »

**Technologies** : FastAPI, Python, MongoDB 8, Motor/Beanie, React 19, Vite, Tailwind, shadcn/ui, JWT, Casbin (RBAC), Mollie (paiements), Firebase (notifications), Docker Compose, Kubernetes, GitHub Actions CI/CD, MinIO/S3

# Questions probables du jury par projet

## Evencia (Frontend + Backend + Mobile)

### Questions techniques générales

1. **« Expliquez-moi le fonctionnement de l'authentification JWT dans votre projet. »**
   > Le client envoie email + mot de passe à POST /api/auth/login. Le backend vérifie le mot de passe avec bcrypt.compare(), puis génère un token JWT signé contenant l'id et le rôle de l'utilisateur. Ce token est renvoyé au client qui le stocke (localStorage côté web, AsyncStorage côté mobile) et l'envoie dans le header Authorization: Bearer <token> à chaque requête. Le middleware authenticateToken vérifie la signature du token, et authorizeRoles vérifie le rôle.

2. **« Pourquoi avoir choisi des UUID plutôt que des auto-incréments ? »**
   > Les auto-incréments sont prévisibles : si je sais qu'un utilisateur a l'id 5, je peux deviner que l'id 6 existe. Avec des UUID (identifiants aléatoires de 36 caractères), il est impossible de deviner les identifiants des autres ressources. C'est une mesure de sécurité qui empêche l'énumération des ressources via l'API.

3. **« Comment fonctionne le paiement Stripe dans votre application ? »**
   > L'utilisateur clique sur "Payer". Le frontend envoie une requête POST /api/payments au backend. Le backend crée une session Stripe Checkout avec le montant et l'événement, et reçoit une URL de redirection. Le frontend redirige l'utilisateur vers cette URL Stripe. Après paiement, Stripe envoie un webhook POST /api/payments/webhook au backend avec le résultat. Le backend vérifie la signature du webhook et met à jour le statut du paiement en base.

4. **« Quelle est la différence entre votre middleware authenticateToken et authorizeRoles ? »**
   > authenticateToken vérifie que le token JWT est valide (signature correcte, non expiré). Il extrait les infos de l'utilisateur et les met dans req.user. authorizeRoles vérifie ensuite que le rôle de l'utilisateur (dans req.user.role) fait partie des rôles autorisés pour cette route. Le premier dit "qui êtes-vous ?", le second dit "avez-vous le droit ?".

5. **« Pourquoi Docker Compose et pas un simple déploiement ? »**
   > Docker Compose permet de lancer les 3 services (MySQL, Backend, Frontend) en une seule commande, avec un réseau isolé et des variables d'environnement centralisées. Ça garantit que l'environnement est identique partout (dev, test, prod), ça évite les conflits de versions, et ça simplifie le déploiement pour quelqu'un qui découvre le projet.

6. **« Expliquez-moi le rate limiting. À quoi ça sert ? »**
   > Le rate limiting limite le nombre de requêtes qu'un client peut faire par minute. J'ai mis 100 req/min en global et 5 req/min sur les routes d'authentification. Ça protège contre les attaques par brute force (essayer des milliers de mots de passe) et contre les DDoS (surcharger le serveur). Si un client dépasse la limite, il reçoit une erreur 429 Too Many Requests.

7. **« Comment gérez-vous les erreurs côté backend ? »**
   > J'ai un middleware centralisé errorHandler qui intercepte toutes les erreurs. Il formate la réponse avec un code HTTP approprié et un message clair. Les erreurs de validation (express-validator) renvoient un 400 avec la liste des champs invalides. Les erreurs d'authentification renvoient 401 ou 403. Les erreurs serveur renvoient 500 sans exposer les détails techniques au client.

8. **« Pourquoi Next.js plutôt que React seul ? »**
   > Next.js apporte le routing par fichiers (App Router), le rendu côté serveur (SSR) pour le SEO, l'optimisation automatique des images, et une configuration zéro pour TypeScript et Tailwind. Pour un projet en production, c'est plus adapté qu'un Create React App qui ne fait que du rendu client.

9. **« Comment fonctionne Zustand dans votre frontend ? »**
   > Zustand est un gestionnaire d'état global léger. J'ai un authStore qui contient l'utilisateur connecté, le token, et les fonctions login/logout/checkAuth. Tous les composants qui ont besoin de l'état d'authentification importent ce store. C'est plus simple que Redux pour un projet de cette taille.

10. **« Pourquoi AsyncStorage sur mobile et pas un cookie ? »**
    > Sur mobile natif (React Native), il n'y a pas de navigateur donc pas de cookies. AsyncStorage est l'équivalent du localStorage pour les applications mobiles : un stockage clé-valeur persistant sur l'appareil. Le token JWT y est stocké et récupéré à chaque lancement de l'app pour maintenir la session.

### Questions sur la base de données

11. **« Expliquez-moi votre schéma de base de données. »**
    > 4 tables principales : users (id UUID, name, email, password hashé, role), events (id, title, description, location, date, price, organizer_id en FK vers users), inscriptions (user_id + event_id avec contrainte UNIQUE pour empêcher la double inscription), et payments (montant, statut, user_id, event_id). Les FK utilisent ON DELETE CASCADE pour la cohérence.

12. **« Qu'est-ce que Drizzle ORM ? Pourquoi l'avoir choisi ? »**
    > Drizzle est un ORM TypeScript-first léger pour Node.js. Il génère des requêtes SQL optimisées et offre un typage fort. Je l'ai choisi car il est plus léger que Sequelize, plus typé, et plus proche du SQL brut (on comprend les requêtes générées).

13. **« Que se passe-t-il si deux utilisateurs s'inscrivent en même temps au même événement ? »**
    > La contrainte UNIQUE KEY unique_user_event (user_id, event_id) dans la table inscriptions empêche la double inscription au niveau de la base. Si deux requêtes arrivent en même temps, la seconde INSERT échouera avec une erreur de contrainte, et mon backend renverra un message "Vous êtes déjà inscrit à cet événement".

### Questions sur le déploiement

14. **« Décrivez-moi votre architecture de production. »**
    > En production, j'ai un docker-compose.prod.yml avec 5 services : MySQL (BDD), Backend (Node.js/Express), Frontend (Next.js), Nginx (reverse proxy qui route les requêtes vers le bon service), et Certbot (renouvellement automatique des certificats SSL). Nginx écoute sur les ports 80 et 443, gère le HTTPS, et proxy les requêtes vers le backend ou le frontend selon l'URL.

15. **« Comment fonctionne le healthcheck MySQL dans votre Docker Compose ? »**
    > Le healthcheck exécute `mysqladmin ping -h localhost` toutes les quelques secondes. Si MySQL ne répond pas après 10 tentatives (timeout 20s chacune), le conteneur est marqué unhealthy. Le backend a `depends_on: mysql: condition: service_healthy`, ce qui signifie qu'il ne démarre que quand MySQL est prêt à accepter des connexions.

## Inside Runway (ir-totalcode)

1. **« Qu'est-ce que Casbin et pourquoi l'utiliser plutôt qu'un simple système de rôles ? »**
   > Casbin est un moteur d'autorisation qui permet de définir des politiques d'accès complexes (RBAC, ABAC). Contrairement à un simple if (user.role === 'admin'), Casbin gère des permissions fines par entité : un styliste peut accéder à SES projets mais pas à ceux d'une autre marque. Les politiques sont stockées en MongoDB et modifiables dynamiquement sans redéployer.

2. **« Quelle différence entre FastAPI et Express.js ? »**
   > FastAPI est un framework Python asynchrone. Il génère automatiquement la documentation OpenAPI à partir des types Pydantic, il est plus rapide qu'Express grâce à l'async natif Python (uvicorn), et il valide automatiquement les entrées/sorties via les schémas Pydantic. Express est plus flexible mais demande plus de configuration manuelle (Swagger, validation).

3. **« Comment fonctionne votre CI/CD avec GitHub Actions ? »**
   > Quand on pousse un tag de version (ex: front-v1.2.0), le workflow GitHub Actions se déclenche. Il builde l'image Docker correspondante, la pousse sur le registry, puis exécute un kubectl apply pour déployer la nouvelle version sur le cluster Kubernetes. C'est du déploiement automatique déclenché par les tags Git.

4. **« Expliquez-moi la différence entre Docker Compose et Kubernetes. »**
   > Docker Compose orchestre des conteneurs sur UNE machine (développement). Kubernetes orchestre des conteneurs sur UN CLUSTER de machines (production). Kubernetes apporte la scalabilité (réplication de pods), la haute disponibilité (redémarrage automatique), le load balancing, et les rolling updates (mise à jour sans interruption).

5. **« Pourquoi MongoDB et pas MySQL pour ce projet ? »**
   > Inside Runway gère des entités très variées (stylistes, marques, collections, looks, articles) avec des structures qui évoluent souvent. MongoDB (NoSQL document) permet de stocker des documents JSON flexibles sans migration de schéma à chaque changement. C'est adapté à un projet en évolution rapide avec des données hétérogènes.

6. **« Comment fonctionne le refresh token ? »**
   > L'access token a une durée courte (ex: 15 min). Quand il expire, le client utilise le refresh token (durée longue, stocké en cookie HttpOnly) pour obtenir un nouvel access token sans redemander le mot de passe. Si le refresh token est compromis, on peut le révoquer via le jti (identifiant unique du token) stocké en base.

7. **« Qu'est-ce que MinIO et pourquoi l'utiliser ? »**
   > MinIO est un serveur de stockage objet compatible avec l'API S3 d'Amazon. En développement, on utilise MinIO en local (dans Docker) pour stocker les fichiers (images, documents). En production, on bascule sur le vrai S3. Ça permet de développer localement sans dépendre d'AWS.

8. **« Comment gérez-vous les WebSockets dans le projet ? »**
   > Les WebSockets sont utilisés pour la messagerie entre utilisateurs (contacts). Contrairement aux requêtes HTTP classiques (requête/réponse), les WebSockets maintiennent une connexion bidirectionnelle permanente. Quand un utilisateur envoie un message, le serveur le pousse immédiatement à l'autre utilisateur sans que celui-ci ait besoin de rafraîchir.

## Bergens

1. **« Décrivez le processus de migration Azure → Scaleway. »**
   > Étapes : 1) Dump de la base PostgreSQL sur Azure (pg_dump). 2) Provisionnement d'une VM Scaleway (Ubuntu). 3) Installation de PostgreSQL, Python, Gunicorn sur la VM. 4) Déploiement du code Django. 5) Import du dump (pg_restore). 6) Configuration de Gunicorn comme serveur WSGI. 7) Installation du certificat SSL. 8) Modification du DNS pour pointer vers la nouvelle IP. 9) Tests de non-régression.

2. **« Pourquoi migrer d'Azure vers Scaleway ? »**
   > L'entreprise souhaitait réduire ses coûts d'hébergement. Azure est puissant mais cher pour un petit site. Scaleway propose des VMs à prix compétitif avec des datacenters en France (conformité RGPD). La migration permettait aussi de simplifier l'infrastructure.

3. **« Qu'est-ce que Gunicorn ? Pourquoi ne pas utiliser le serveur Django directement ? »**
   > Le serveur de développement Django (manage.py runserver) n'est pas conçu pour la production : il est mono-thread et pas sécurisé. Gunicorn est un serveur WSGI de production qui gère plusieurs workers (processus), le load balancing entre eux, et les timeouts. C'est le standard pour déployer Django en production.

4. **« Comment Django gère-t-il la sécurité ? »**
   > Django intègre nativement : la protection CSRF (token dans les formulaires), le hash des mots de passe (PBKDF2 par défaut), la protection contre les injections SQL (ORM avec requêtes paramétrées), la protection XSS (échappement automatique des templates), et un système de permissions/groupes pour l'autorisation.

5. **« Qu'est-ce que Django REST Framework ? »**
   > DRF est une extension de Django qui facilite la création d'APIs REST. Il fournit des serializers (conversion modèle ↔ JSON), des viewsets (CRUD automatique), l'authentification par token, la pagination, et une interface web navigable pour tester l'API directement dans le navigateur.

## ActionCulturel (dz)

1. **« Pourquoi utiliser Redis en plus de MySQL ? »**
   > Redis est une base de données en mémoire (in-memory) ultra-rapide. Je l'utilise comme cache : les données du patrimoine culturel (sites, œuvres) qui changent rarement sont mises en cache dans Redis. Quand un utilisateur consulte un site culturel, on regarde d'abord dans Redis (instantané) avant d'aller en MySQL (plus lent). Ça améliore les temps de réponse.

2. **« Quelle est la différence entre ActionCulturel et Evencia techniquement ? »**
   > Les deux utilisent Node.js + Express + React + MySQL + Docker, mais ActionCulturel ajoute Redis pour le cache et gère un domaine métier différent (patrimoine culturel vs événements). ActionCulturel a aussi le support multilingue (FR/AR/EN) et des types de données plus variés (sites archéologiques, œuvres d'art, artisanat).

3. **« Comment gérez-vous le multilingue ? »**
   > Les données sont stockées en base avec des champs par langue (title_fr, title_ar, title_en) ou un champ JSON contenant les traductions. L'API accepte un paramètre de langue et renvoie les données dans la langue demandée. Côté frontend, l'interface utilise une librairie d'internationalisation (i18n) pour les textes statiques.

## Questions transversales (tous projets confondus)

1. **« Quelle est la différence entre authentification et autorisation ? »**
   > L'authentification vérifie l'identité ("qui êtes-vous ?" → login/mot de passe → token). L'autorisation vérifie les droits ("avez-vous le droit de faire ça ?" → vérification du rôle). Dans Evencia : authenticateToken = authentification, authorizeRoles = autorisation.

2. **« Qu'est-ce qu'une API REST ? »**
   > Une API REST est une interface qui permet à des applications de communiquer via HTTP. REST impose des conventions : utiliser les verbes HTTP (GET pour lire, POST pour créer, PUT pour modifier, DELETE pour supprimer), des URLs qui représentent des ressources (/api/events, /api/users), et des codes de retour standardisés (200, 201, 404, etc.).

3. **« Qu'est-ce que le CORS et pourquoi est-ce nécessaire ? »**
   > CORS (Cross-Origin Resource Sharing) est un mécanisme de sécurité des navigateurs. Par défaut, un site web ne peut pas faire de requêtes vers un autre domaine. Si mon frontend est sur localhost:3000 et mon API sur localhost:5000, le navigateur bloque les requêtes. Le CORS configure le serveur pour autoriser les requêtes depuis certaines origines.

4. **« Expliquez la différence entre SQL et NoSQL. »**
   > SQL (MySQL, PostgreSQL) : données structurées en tables avec un schéma fixe, relations entre tables (FK), requêtes SQL, transactions ACID. NoSQL (MongoDB) : données en documents JSON flexibles, pas de schéma rigide, scalabilité horizontale facile, adapté aux données hétérogènes. J'ai utilisé les deux selon les besoins du projet.

5. **« Comment gérez-vous les conflits Git ? »**
   > Quand deux personnes modifient le même fichier, Git signale un conflit au moment du merge. J'ouvre le fichier, je vois les marqueurs (<<<<, ====, >>>>), j'analyse les deux versions, je choisis la bonne (ou je combine), je retire les marqueurs, puis je commit la résolution.

6. **« Qu'est-ce que Docker ? Pourquoi l'utiliser ? »**
   > Docker permet de packager une application avec toutes ses dépendances dans un conteneur isolé. L'avantage : "ça marche sur ma machine" → "ça marche partout". Un Dockerfile décrit comment construire l'image, et docker-compose orchestre plusieurs conteneurs ensemble (API + BDD + Frontend).

7. **« Quelle est la différence entre bcrypt et Argon2 ? »**
   > Les deux sont des fonctions de hash pour mots de passe. bcrypt est le standard historique (utilisé dans Evencia). Argon2 est plus récent (vainqueur de la Password Hashing Competition 2015), plus résistant aux attaques GPU et configurable en mémoire/temps. Je l'ai utilisé dans Inside Runway car c'était le choix de l'équipe.

8. **« Comment testez-vous vos APIs ? »**
   > Plusieurs niveaux : 1) Tests unitaires Jest pour la logique métier. 2) Tests d'intégration Postman/Swagger pour vérifier chaque endpoint (cas nominal + cas d'erreur). 3) Tests manuels en navigateur/mobile pour le parcours utilisateur complet. Pour Evencia j'ai 42 requêtes Postman qui couvrent tous les endpoints.

9. **« Que se passe-t-il quand le token JWT expire ? »**
   > Le middleware authenticateToken vérifie l'expiration. Si le token est expiré, jwt.verify() échoue et renvoie une erreur 403 "Token invalide". Le client doit alors rediriger vers la page de connexion. Dans Inside Runway, il y a un refresh token qui permet de renouveler l'access token sans se reconnecter.

10. **« Pourquoi séparer frontend et backend ? »**
    > L'architecture découplée (SPA + API) offre plusieurs avantages : le même backend sert le web ET le mobile (pas de duplication), chaque partie peut évoluer indépendamment, on peut changer le frontend sans toucher au backend (et inversement), et le déploiement est plus flexible (Vercel pour le front, Render pour le back).
